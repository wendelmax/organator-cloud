# Release 2.1.0 Versioning Design

## Goal

Align every first-party npm workspace with the milestone 5 release by publishing a single coherent project version: `2.1.0`.

## Scope

Update the `version` field in the root manifest and every first-party app/package manifest:

- `package.json`
- `apps/backoffice-web/package.json`
- `apps/control-plane-api/package.json`
- `apps/provisioner-worker/package.json`
- `packages/cloud-providers/package.json`
- `packages/core-models/package.json`
- `packages/ui/package.json`

Regenerate `package-lock.json` so its root and workspace package metadata match the manifests. Dependency ranges and resolved dependency versions must not change.

## Release Flow

1. Apply the manifest versions on a dedicated release branch.
2. Regenerate lockfile metadata with npm.
3. Verify all first-party manifests and lockfile workspace entries report `2.1.0`.
4. Run clean dependency installation, lint, and builds using the CI workflow contract.
5. Open a release-version PR against `main`.
6. After merge, synchronize local `main`, then create Git tag and GitHub release `v2.1.0`.

## Safety and Rollback

This release contains metadata-only changes. It introduces no schema, runtime, API, or dependency changes. Rollback consists of reverting the version commit before tagging; an existing published tag must not be moved or overwritten.

## Acceptance Criteria

- All seven first-party manifests report `2.1.0`.
- Relevant root/workspace entries in `package-lock.json` report `2.1.0`.
- Dependency specifications and resolved packages are unchanged.
- CI lint and build pass.
- The version PR is merged before `v2.1.0` is tagged or released.
